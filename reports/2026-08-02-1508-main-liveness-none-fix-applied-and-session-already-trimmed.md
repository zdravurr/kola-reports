## 1. §4 — ПРИМЕНЕНО И ПОДТВЕРЖДЕНО В БОЮ

`scripts/main_liveness.py:149`

```python
    res = ping_main()
    # None = «НЕ СПРАШИВАЛИ» (стоп :84 или нехватка памяти :70), а не «мёртв».
    if res is None:
        log("[skip] пинг не выполнялся (стоп/память) — это НЕ отказ main. "
            "Ни рестарта, ни тревоги; счётчик отказов не трогаю.")
        return
    if res:
        ...
```

Под `None` не трогается **ничего**: ни гейтвей, ни тревоги, ни `last_ok`, ни счётчик.

### 🔴 Источников `None` оказалось ДВА, а не один

Кроме аварийного стопа (`:84`) то же самое значение возвращает **мем-гвард** (`:70`):
`MemAvailable < MIN_MEM_PCT` → «не поднимаю агента ради пинга». В журнале он срабатывал
1 раз — то есть каждый раз, когда машине не хватало памяти, сторож в ответ **перезапускал
гейтвей и кричал «Money-path СТОИТ»**. Правка лечит оба источника разом, потому что
проверяет `is None`, а не конкретную причину.

### Проверка

| шаг | факт |
|---|---|
| Бэкап | `main_liveness.py.bak_none_vs_false_20260802` + `main_liveness.json.bak_20260802` |
| `ast.parse` под botuser | OK |
| Владелец после правки из-под root | 🔴 стал `root:root` — **пойман и возвращён** `botuser:botuser`, 755 |
| Ручной `--dry` 14:52:00 | `[ping] АВАРИЙНЫЙ СТОП…` → `[skip] пинг не выполнялся…` → выход |
| **Штатный крон 15:00:01** | `[ping] АВАРИЙНЫЙ СТОП…` → **`[skip] …`** |
| Рестартов гейтвея после 14:52 | **0** |
| Тревог «НЕ ОТВЕЧАЕТ» / «НЕ ОЖИЛ» после 14:52 | **0** |

Ничего не перезапускал: `main_liveness` — крон-скрипт, демона у него нет. Гейтвей не трогал.

**Было:** 88 рестартов + 176 тревог в сутки. **Стало:** 0 и 0 на первом же штатном прогоне.

## 2. `consecutive_fail` — ДА, НУЖЕН СБРОС. СБРОШЕН

Состояние до правки:

```
last_ok          = 2026-07-28 15:10:02Z      («молчит ~119,6 ч» по мнению сторожа)
consecutive_fail = 718
last_heal        = 2026-07-26 22:13:28Z
```

**718 инкрементов — это не отказы.** Это 718 раз «мы не спрашивали». Счётчик читает
**только сам сторож** (проверено `grep` по всему workspace) и используется лишь в строке
лога, поэтому порчи чужой логики не было — но отравленное число рано или поздно вводит
в заблуждение. **Сброшен в 0**, в файл добавлена пометка о причине.

🔶 **`last_ok` намеренно НЕ тронут.** Поставить его «сейчас» означало бы записать
подтверждённую живость, которой у нас нет: мы не спрашивали `main` пятые сутки.
Побочный эффект: первая **настоящая** тревога после снятия стопа скажет «висит ~120 ч»,
хотя правильнее было бы «не спрашивали 120 ч». Это дефект формулировки `down_min`
(считается от последнего УСПЕХА, а не от последнего ВОПРОСА) — **записываю как отдельный
мелкий пункт, не правлю**: врать в другую сторону хуже.

Это **не** сессии `main`. Это транскрипты бэкенда `claude-cli` в `~/.claude/projects/`,

То есть все три замерли **до/около** правки 06.07. А транскрипты, которые реально росли

## 4. ЗАПИСАНО НА ПОТОМ, НЕ СДЕЛАНО

### §3-C — фильтр по возрасту последнего турна (ТЕПЕРЬ ЭТО ГЛАВНЫЙ РЫЧАГ)

Вы просили C **после** E. E оказался уже выполненным — значит **C становится первым и
единственным рычагом** на этом направлении.

Форма: перед платным пингом смотреть возраст последнего турна `main` (файл сессии /
`lastInteractionAt` в `sessions.json`, обе величины уже на диске и читаются без модели).
Свежий турн (< 30 мин) → пинг не нужен, `main` заведомо жив. Только молчание дольше порога
поднимает платный пинг.

Эффект при снятом стопе: из 144 пингов/сут остаются единицы — те, где `main` действительно
давно молчит. **Проверяемое свойство сохраняется полностью:** зависший цикл (`rc=0`,
пустой stdout) по-прежнему ловится, просто мы перестаём спрашивать того, кто только что
отвечал. Риск: порог надо выбрать так, чтобы он был меньше времени, за которое зависший
`main` успевает навредить.

### §5 — фильтр headless в хуке `SessionStart`

**Записано, не делаю** — по вашему решению и по собственным цифрам: сейчас это **0,7 М/сут**,
множитель, а не источник. Форма на будущее: в самой команде хука проверять
`CLAUDE_CODE_ENTRYPOINT` и для `sdk-cli` не выводить `ACCOUNTS.md`/`STATUS.md`.

### Мелочь оттуда же

`down_min` в тревоге считается от последнего **успеха**, а не от последнего **вопроса** —
после долгого стопа даст завышенное «висит ~N часов». Косметика, но вводит в заблуждение.
