## Коротко

Все пять пунктов закрыты. Плюс по дороге нашлась поломка **старше самой задачи**: почтовая
воронка по соц-лидам была мертва целиком и молча — **350 падений** на опечатке в одну строку.

**Прямой ответ на твой вопрос: IMAP IDLE телефон не трогает ВООБЩЕ.** Ни при ожидании,
ни при разборе письма. Телефон нужен только когда дело доходит до реального ответа на
площадке. Доказано кодом, не на словах — ниже.

## 1. ⛔ Экран больше не будится по расписанию

Было: `pixel_keepalive.sh` каждые 15 минут слал `KEYCODE_WAKEUP` и переставлял
`screen_off_timeout=1800000` — то есть **будил телефон ровно чтобы он не заснул**.

Замер показал, что это было не нужно уже давно:

```
settings get global stay_on_while_plugged_in  →  7     (не гаснет на зарядке)
dumpsys power                                 →  mWakefulness=Awake
```

Телефон на зарядке и так не засыпает. Выбран **первый** из предложенных тобой вариантов —
продлить собственный таймаут телефона:

```
settings put system screen_off_timeout 2147483647    (~24.8 суток, персистентно)
```

`KEYCODE_WAKEUP` из скрипта **удалён**. Проверка после правки:

```
исполняемых KEYCODE_WAKEUP:   0
исполняемых screen_off_timeout: 0
[keepalive] 15:21 мост/нода проверены (экран НЕ будился — таймаут держит сам телефон)
экран: Awake      таймаут: 2147483647
```

Если телефон когда-нибудь снимут с зарядки И настройку собьют — экран погаснет, и его
разбудит **первый же экранный шаг, прямо перед работой**. Это и есть правило, которое ты
задал: будим перед задачей, а не по будильнику.

Что осталось в скрипте: живость CDP-моста и OpenClaw-ноды. Экран не трогает.
⚠️ Честно: ярусы CDP в нём **дублируют** `cdp_bridge_guard.sh` (*/5), который и так единый
лекарь всех трёх ярусов. Не сносил — это уже за рамками приказа; скажи, сложу.

## 2. 📬 Почта: опрос */15 → IMAP IDLE

`projects/sales/mail_idle_watch.py`, демон `kola-mail-idle.service` (systemd --user, **не крон**).
Крон `*/15` снят меткой `#REPLACED_BY_IMAP_IDLE_27AUG`, активных `mail_watch --once` — **0**.

Соединение висит, сервер сам толкает. Оба ящика на IDLE:

```
15:19:55  [ring] катч-ап на старте → scan() отработал за 12.6с
15:19:56  [2r] zdravurr@gmail.com:  IDLE установлен (refresh 540с)
15:19:56  [4r] zdravurrrr@gmail.com: IDLE установлен (refresh 540с)
```

### Доказано живьём — настоящим письмом

SMTP наружу закрыт, поэтому положил письмо в ящик через IMAP `APPEND` со **второго**
соединения. Это и есть чистая проверка: сервер обязан сам толкнуть тому, кто висит в IDLE.

```
15:25:13.990   APPEND -> OK                        ← письмо появилось в ящике
15:25:27.263   [2r] 📬 сервер толкнул: новое письмо  ← 13.3 с, сервер сам
15:25:58.280   [ring] 2r/IDLE → scan() отработал за 31.0с
               → обратно в IDLE
```

**Было до 15 минут ожидания — стало 13 секунд.** Письмо-проба после теста удалено из ящика.
Покупателя не изображало и под фильтры `SIGNALS` не попадало — лид из него родиться не мог.

### Границы, которые модуль не переступает

- **Он только звонок.** Разбор, дедуп и роутинг делает всё тот же `mail_watch.scan()`.
  Копии логики нет намеренно: две копии разъезжаются, и два судьи одного факта начинают
  спорить.
- **Катч-ап на старте и после каждого обрыва.** IDLE толкает только НОВОЕ; пришедшее «не
  при нас» иначе пропало бы навсегда.
- **`IDLE_REFRESH_S=540` — это не опрос.** Gmail рвёт висящий IDLE, RFC 2177 требует
  переоткрытия. Всё это время сервер может толкнуть в ту же секунду. Мы не спрашиваем
  «есть ли почта» — мы держим открытую дверь.
- Python 3.12: `imaplib.idle()` появился только в 3.13, поэтому IDLE поднят вручную поверх
  сокета, с проверкой `ssl.pending()` — `select()` не видит уже расшифрованный буфер, и без
  этого письмо, пришедшее в момент постановки на IDLE, ждало бы полного refresh.

## 3. 🔴 ТВОЙ ВОПРОС: трогает ли IDLE телефон

**Нет. Ни разу — ни в ожидании, ни при разборе письма.**

Проверил не рассуждением, а поиском по коду всех способов дотянуться до телефона
(`adb`, `ssh`, `KEYCODE`, `screencap`, `uidump`, `input tap`, `vtap`, IP телефона):

| Файл | Обращений к телефону |
|---|---|
| `mail_idle_watch.py` (ожидание + звонок) | **0** |
| `mail_watch.py` (разбор письма) | **0** |

В `mail_watch.py` слово `phone_hands` встречается — но только **внутри текста задания**,
которое отправляется воркеру, а не как вызов. Сам модуль телефон не трогает.

Как это устроено физически: IDLE — это TCP/SSL-соединение **с сервера к imap.gmail.com**.
Телефон в этой цепочке не участвует вообще. Он нужен ровно на последнем шаге — когда надо
**реально ответить на площадке**, и туда идёт `worker_task_runner`, уже под замком экрана и
анти-баном. Ожидание почты и работа с телефоном полностью развязаны.

## 4. 🔴 Найдена поломка старше задачи: воронка была мертва

При первом же запуске `scan()` упал:

```
TypeError: bad operand type for unary +: 'str'
  mail_watch.py:336  в _route_social_to_ogon
```

Причина — **лишний `+` в конце строки**:

```python
+ lane_line +          ← вот он
+ (_tail3 + "\nОТКРОЙ тред через phone_hands …
```

Получалось `lane_line + (+"...")` — унарный плюс к строке.

**В логе 350 падений.** И падало не в пустоте: строкой выше стоит
`HIT [Facebook-соц] … Ricardo Mercado отправил вам сообщение` — письмо **детектировалось**,
а через строку весь проход умирал. То есть почтовая воронка по соц-лидам была мертва
целиком, и молча: крон писал traceback в свой же лог, куда никто не смотрел.

Класс тот же, что и весь день: **зелёная метрика без проверки факта**. Крон отрабатывал
«успешно» (rc крона никого не волновал), а работа не делалась.

Исправлено. После правки: `scan() отработал за 12.6с`, затем 31.0с на реальном звонке.
Других таких опечаток в файле нет (проверил).

## 5. node_notif_watch (*/3) — событийным сделать НЕЛЬЗЯ

Спросил у самой ноды, что она умеет:

```
openclaw nodes describe → поддерживаемые команды:
    notifications.list
    notifications.actions
```

**Подписки нет.** Ни `subscribe`, ни `stream`, ни `watch` — API ноды **только на вытягивание**.
(`canvas.a2ui.push` — это push в обратную сторону, хост→нода.) Пока нода не научится
толкать сама, событийным этот детектор не сделать. Оставил как есть, как ты и разрешил.

Стоит знать: это **резервный** детектор. Первичный — демон `inbox_watcher` (25с, трей
уведомлений). Путь к полной событийности существует: у AutoJs6 на телефоне есть
NotificationListenerService, а `kola-bridge.service` (long-poll телефон↔хост) уже работает —
но это отдельная работа на самом телефоне, не правка крона.
