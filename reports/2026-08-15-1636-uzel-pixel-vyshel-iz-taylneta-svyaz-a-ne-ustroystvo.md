## 1. ЧТО ИМЕННО СЛОМАНО — с точностью до узла и минуты

Сервер здоров: `tailscaled` active, свой адрес `100.109.145.94`, ключ до 07.12.

Узел телефона в тайлнете:

```
HostName      : Pixel 10a          DNSName : pixel-10a-2.tail523420.ts.net
Online        : False
LastSeen      : 2026-08-15T15:30:00Z      ← замолчал в 15:30 UTC
LastHandshake : 0001-01-01T00:00:00Z      ← рукопожатия НЕ БЫЛО ВООБЩЕ
KeyExpiry     : 2026-12-12T16:43:22Z      ← ключ НЕ истёк (ещё 4 месяца)
CurAddr       : (пусто)   Relay: iad
TxBytes       : 10764     RxBytes : 0     ← мы шлём, в ответ НОЛЬ
```

**`RxBytes: 0` — это весь диагноз в одном числе.** Наши пакеты уходят, обратно не приходит
ничего. Не «медленно», не «теряется» — ноль байт с момента разрыва.

Проверено всеми путями, каждый молчит:

| путь | результат |
|---|---|
| `ping 100.85.178.10` | 100% loss (трижды: 15:59, 16:17, 16:28) |
| `tailscale ping` ×5 | `no reply` — не пробивается даже через relay |
| `ssh -p 8022 u0_a313@…` | `Connection timed out` |
| `adb devices` | пусто |
| `adb connect …:5555` | timeout 20 с (то же и в кроне дирижёра, 16:28) |
| **документированное восстановление** `pixel_ssh.relink(wake=True)` | **False**, `preflight` → **False** |

### Ответы на поставленные вопросы

1. **VPN с обеих сторон?** Сервер — да. **Телефон — НЕТ**: координатор не слышал узел
   58 минут, `LastHandshake` пустой. В сети телефона нет.
2. **Жив ли adb/мост на телефоне?** Мост на СЕРВЕРЕ жив (`server.py` pid 1001401,
   `/health` → ok, слушает 0.0.0.0:8765). Но телефон в него не стучится, и adb до него не
   доходит: **все наши каналы (ssh, adb, мост) идут ПОВЕРХ тайлнета**. Нет тайлнета — нет
   ни одного канала. Проверить, жив ли adbd на самом устройстве, с сервера физически нельзя.
3. **Сменился ли IP?** **Нет.** `100.85.178.10` по-прежнему закреплён за `pixel-10a-2`
   (Tailscale раздаёт стабильные адреса). Конфиги менять не нужно — они верны.

### Вывод

**Tailscale на самом Pixel перестал быть подключённым в 15:30 UTC.** Ключ жив, адрес жив,
сервер жив — замолчал клиент на устройстве. Типичная причина на Android: система усыпила
или выгрузила VPN-сервис (Doze/battery optimization), либо тумблер VPN сняли, либо приложение
смахнули из недавних.

**С сервера это НЕ ЧИНИТСЯ** — что и подтвердил `relink → False`. Нужны 20 секунд на телефоне.

## 2. 🔴 ПОБОЧНАЯ НАХОДКА, КОТОРАЯ ДОРОЖЕ САМОГО ОБРЫВА

Разбираясь, я наткнулся на след: система «смотрела на экран» уже ПОСЛЕ того, как телефон
пропал. Причина нашлась в `screen_read.read_screen` — возврат `screencap` **выбрасывался**:

```python
_px.screencap(_SCR)          # ← результат никто не читал
return {"source": "uidump", "elements": ui, "screenshot": _SCR}
```

При **ЧАСТИЧНОМ** отказе связи (дерево UI ещё приходит, снимок уже нет) `screencap` возвращает
False и файл `_SCR` **не перезаписывается** — на диске остаётся **ПРЕДЫДУЩИЙ кадр**. Путь к
нему отдавался как к ТЕКУЩЕМУ экрану, и глаза уверенно судили об экране, которого уже нет.

**Почему это дороже обрыва: этот путь ВЕДЁТ РУКУ.** Понимание экрана превращается в тап.
Судить по старой картинке и тапать по сегодняшнему экрану — это слепой тап, запрещённый
прямо, только замаскированный под зрячий.

Полный отказ фейлился закрыто и раньше (нет дерева → нет снимка → `source=none`). Дыра была
ровно в ЧАСТИЧНОМ — **том самом, что и случился сегодня**.

**Исправлено** (`d266f25`): кадр не обновился → `screenshot=None`. Элементы из живого дерева
отдаём (они настоящие), старую картинку за текущую — нет. Доказано воспроизведением:
контракт подменяет `pixel_ssh`, кладёт заведомо старый кадр и требует, чтобы он не был
предъявлен; плюс проверка, что нормальный путь не сломан и что глаза на пустом кадре вообще
не зовут модель. Контрактов стало **15/15**.
