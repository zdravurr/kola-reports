### 1.4 ⚠️ ПЛЕЧО НА БИРЖЕ — **НЕ 5×**
```
longLeverage = 10      shortLeverage = 20      (макс 150)
```
Бот зовёт `set_leverage(5)` в `market_entry`, но **этот вызов warn-only**: упал — печатается
предупреждение, вход продолжается.

**Что это меняет и чего НЕ меняет.** Размер позиции бот считает сам:
`amount = 30 × 5 / price = 0.002327 BTC`, то есть **$150 нотионала при любом плече на бирже**.
Биржевое плечо влияет на **занятую маржу и дистанцию до ликвидации**, а не на размер:

| плечо на бирже | занятая маржа | стоп 2.5×ATR ≈ 1.26 % | ликвидация |
|---|---|---|---|
| 5× (как задумано) | $30 | далеко до ликвидации | ~20 % |
| 10× (сейчас LONG) | $15 | тот же | ~10 % |
| 20× (сейчас SHORT) | $7.5 | тот же | ~5 % |

Стоп срабатывает **сильно раньше ликвидации во всех трёх случаях**, так что это не опасность.
Но если `set_leverage` упадёт, баннер скажет «x5», а на бирже будет 10×/20×. **Несоответствие
между заявленным и фактическим — а мы весь день чинили ровно этот класс.**

### 1.5 ⚠️ РЕЖИМ МАРЖИ — **CROSSED**, а код говорит «isolated»

## 4. ТОЧНАЯ ПОСЛЕДОВАТЕЛЬНОСТЬ ФЛИПА — прочитай до того, как я её выполню

**Файл ровно один: `/root/titan-bot/config.py`. Две строки.**


**Ничего больше не трогается.** Уже стоят и остаются как есть:
```

строка  83:  PASSIVE_FILL_RECONCILE_EXISTS = True    (снят пунктом 13)
```

**ПЕРЕЗАПУСК ОБЯЗАТЕЛЕН.** `gunicorn.conf.py` содержит `preload_app = True` и **не имеет** директивы
`reload` (проверено: 0 вхождений). `config` импортируется на загрузке модуля, а оба загрузочных
гейта живут в `when_ready`, то есть исполняются только при старте мастера:
```
systemctl restart titan.service
```

**Порядок, который я бы выполнил:**
1. Ещё раз убедиться, что открытых позиций **0** (иначе 12c откажет в старте).
2. Правка двух строк.
3. `python3 -m py_compile config.py`.
4. `git add -A titan-bot/ && git commit` — флип фиксируется в истории, а не живёт только на диске.
5. `systemctl restart titan.service`.
6. Немедленно смотреть журнал: баннер обязан показать **🔴 LIVE ORDERS · $30 × 5 = $150**.
7. Смотреть первую сделку живьём.

**Откат — те же две строки обратно + рестарт.** Пока позиции нет, откат мгновенный и полный.

## 5. ЧТО СМОТРЕТЬ НА ПЕРВОЙ СДЕЛКЕ, ПО ПОРЯДКУ

### Шаг 0 — сразу после рестарта
✅ **норма:**
```
[ORDER-MODE] 🔴 LIVE ORDERS — REAL MONEY: orders ARE sent to BingX
[ORDER-MODE]   LIVE_TRADING_ENABLED = True   ORDER_ADAPTER_LIVE = True
[ORDER-MODE]   sizing: margin $30 x 5 = $150 notional per entry
```
🔴 **проблема:** видишь `🛑 REFUSING TO START` → один из гейтов сработал; при `exit 3` сервис уйдёт
в цикл рестартов раз в 5 с. Читай саму строку CRITICAL — она называет причину и Fix.

### Шаг 1 — ВХОД
✅ **норма:** `[ADAPTER] LIVE ENTRY BTC/USDT:USDT LONG 0.0023 @ <цена> fee=<реальная>`
затем `VIRTUAL ENTRY vpos=<N> ... sl=<цена>`

🔴 **провал входа выглядит так:**
- `[ADAPTER] ENTRY REFUSED ... below minimum` → размер не прошёл минимум. Позиции нет, строки нет. Безвредно.
- `VIRTUAL ENTRY ABORTED ... adapter refused the order` → то же.
- **исключение из `create_market_order`** → в журнале traceback, строки нет, позиции нет.
- ⚠️ **`[ADAPTER] set_leverage warn:`** → вход ПРОДОЛЖИТСЯ на биржевом плече 10×/20× (§1.4). Не остановка, но заметь.
- ⚠️ **`🔴 PARTIAL FILL on entry ... asked X, filled Y`** → пункт 14 не реализован, позиция останется частичной. Размер вниз по потоку берётся исполненный, так что арифметика согласована — но позиция меньше задуманной.

### Шаг 2 — ПОСТАНОВКА СТОПА (самое важное место)
✅ **норма:** `[ADAPTER] LIVE STOP BTC/USDT:USDT LONG @ <цена> id=<order id>`
и в БД у строки заполнен `stop_order_id`.

🔴 **провал постановки стопа:**
```
[BE-SL-RETRY] attempt 1/3 ... 2/3 ... 3/3 failed
[ADAPTER] 🚨 STOP PLACEMENT FAILED ... firing the emergency close invariant
🚨 SL PLACEMENT FAILED  (Telegram)  ->  ✅ Emergency close executed
VIRTUAL ENTRY ABORTED ... no row written
```
**Это КОРРЕКТНОЕ поведение**, а не авария: позиция закрыта по рынку, строка не написана.
**По-настоящему плохо** — если увидишь `CRITICAL: emergency close itself failed`. Тогда на бирже
осталась **живая позиция без стопа**, и это ручное вмешательство немедленно.

### Шаг 3 — СИРОТСКИЙ СТОП (гонка на входе)
🔴 `🚨 ORPHAN STOP COULD NOT BE CANCELLED ... MANUAL ACTION REQUIRED` → стоп висит над **чужой**
позицией на неверном уровне. Руками, сразу.

### Шаг 4 — ВЫХОД ПО СТОПУ
✅ **норма (пункт 13 работает):**
```
[VPOS-FILL] passive fill vpos=N ... stop-loss filled @ <цена> fee=<реальная> reason=sl
```
плюс обычный close-report в Telegram, а строка в БД становится `status='closed'` с реальным P&L.
После безубытка ожидай `reason=breakeven`, а не `sl`.

🔴 **СЛУЧАЙ C — тот, ради которого всё это строилось:**
```
[VPOS-FILL] 🚨 vpos=N: position GONE from the exchange but our stop <id> did NOT fill.
            NOT closing the row — exit price unknown. MANUAL ACTION REQUIRED.
🚨 POSITION GONE, STOP DID NOT FILL  (Telegram)
```
Значит позицию закрыло **не наше**: руки, ликвидация, действие биржи. Строка ОСТАЁТСЯ открытой,
цену мы не выдумываем, **и эта сторона заблокирована для новых входов**, пока ты не разберёшь.

🔴 **МОЛЧАНИЕ — тоже симптом.** Если позиция на бирже закрылась, а в журнале **ни** `[VPOS-FILL]`,
**ни** close-report — значит сверка не отработала. Проверь `select status from virtual_positions
where id=N`: если `open`, это возврат той самой дыры §6 пункта 12.

### Шаг 5 — ПРОВЕРКА ДОПУЩЕНИЯ `closePosition='true'` (§4.1 прошлого отчёта)
Это **единственная вещь, которую нельзя проверить иначе, чем живой сделкой.** Смотри на бирже
**сразу после входа**:
- ✅ **норма:** ровно **ОДИН** ордер `STOP_MARKET` с `closePosition=true` на нужной стороне.
- 🔴 **допущение неверно, если:** ордеров два; или стоп имеет конкретный `quantity` вместо
  «закрыть позицию»; или после безубытка старый стоп остался рядом с новым.
- 🔴 **и главное — на выходе:** позиция должна уйти в **0**. Если после срабатывания стопа
  осталась ненулевая позиция или, хуже, **перевёрнутая** — `closePosition` работает не так, как мы
  предположили, и надо немедленно возвращать флаги в False.
