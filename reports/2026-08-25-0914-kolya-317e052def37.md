# 317e052def37 — 5 (по факту 6) запаркованных тредов молчали навсегда: леджер снят

## Что было сломано
Фикс `3d37a6658ad7` научил свип роутить запаркованный WAITING-тред при ПЕРВОМ взгляде,
но смотрит он только на **отсутствие** записи в `.kola_state/fb_parked_rows.json`.
У тредов, которые уже получили свой «один раз» по СТАРОЙ логике (skip-once **без**
роутинга), запись в леджере уже лежала. Ветка `was == h` в `drop_parked_unchanged`
гасила их как чурн — навсегда, пока покупатель не напишет снова. А покупатель уже
написал: он там говорил ПОСЛЕДНИМ.

## Улика — живьём, не по рассуждению
Тред попадает в `drop_parked_unchanged` только если `classify` уже назвал его WAITING,
то есть «последним в строке инбокса говорил ПОКУПАТЕЛЬ». В боевом логе свипа эти треды
гасятся каждым прогоном подряд двое суток:

```
2026-08-24T11:16 / 20:45 / 23:15 · 2026-08-25T02:45 / 06:15
  [parked-skip] Alaine F. / George / Waseem / Heather / Anita / Michelle
  — отработан (парковка), строка инбокса НЕ менялась → не роутю
```

Ни у одного из них в боевом логе нет `[parked-new]` — значит route-once по новой
логике им **ни разу не доставался**. Это и есть «не отвечены»: строка инбокса — самый
сильный источник, который в этом же файле объявлен главнее бейджа непрочитанного.

## Почему снятие безопасно (blast radius)
Леджер переписывается каждым прогоном тем, что видели ЭТИМ взглядом, поэтому снятие
не нужно «удерживать»: следующий свип увидит `was is None` → `[parked-new]` → **роутит
один раз** и запоминает строку. Дальше неизменная строка снова гасится как чурн — ничего
не зациклится.

Роутится не «вслепую»: до `drop_parked_unchanged` доходят только треды, которые
`classify` **на этом же прогоне** назвал WAITING. Если покупателю за это время ответили —
тред просто не дойдёт сюда, и его запись тихо исчезнет из леджера. То есть повторная
валидация «отвечен или нет» происходит сама, на свежих данных, а не по моему снимку.
