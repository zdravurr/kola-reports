# Гейтвей больше не перезапускает живую сессию из-под работающего хода

**Что ломалось.** Гейтвей держит ОДНУ живую сессию `claude` на ключ сессии и
переиспользует её. Второй ход, пришедший на тот же ключ `agent:<id>:main`,
перезапускал сессию из-под первого (`claude live session close … reason=restart`,
23.08 17:00–19:50, activeSessions до 6), и у первого рвалась MCP-петля:
`mcp__openclaw__*` отвечали «Unable to connect» или исчезали как «No such tool
available» при живом (http200) гейтвее.

Замок «один ход на агента» такую пару не ловил В ПРИНЦИПЕ: он видит только ходы,
поднятые через `wake()` (процесс `openclaw agent` в `ps`). Ход, который гейтвей
заводит сам — сообщение Босса в Telegram, его собственный крон — процессом не
светится. Сталкивалась ровно такая пара.

**Что починил.** Развёл ЛАНЫ, а не время. Наши автоматические ходы уезжают на
отдельный ключ `agent:<id>:auto`; `agent:<id>:main` остаётся гейтвею. Это разные
живые сессии — чужой ход физически не может перезапустить нашу.

- `lib/agent_capacity.py` — `turn_session_key()`: единая дверь подмены ключа,
  ровно на границе спавна. Выше по коду цель остаётся ЛОГИЧЕСКОЙ (`:main`) —
  по ней считают занятость, дедуп, канал доставки и аудит.
- `wake()` теперь ставит `--session-key` ВСЕГДА. Раньше без ключа гейтвей сам
  клал ход в `agent:<id>:main` — то есть в сессию, которую делит с Боссом.
- `scripts/commit_watchdog.py` — собирает `openclaw agent` сам, мимо `wake()`;
  ходит той же дверью, иначе продолжал бы рестартить сессию Босса.
- `scripts/main_liveness.py` — пинг намеренно остаётся на `:main` (он для того и
  есть, чтобы ловить зависшую ГЛАВНУЮ сессию), но теперь УСТУПАЕТ живому ходу:
  идущий ход и есть доказательство жизни, ради которого пинг затевался.
- Лана рантайма `agent:<id>:subagent:<uuid>` — чужая, не переписывается.

**Почему лана, а не уникальный ключ на каждый ход.** Ключ-на-ход тоже закрывает
класс, но каждый заводит новую запись в реестре сессий гейтвея (у worker3 там уже
65 ключей от subagent-спавнов, прибирать их никто не умеет) — чинили бы столкновение
ценой неограниченного роста состояния. Одна выделенная лана даёт РОВНО ОДНУ лишнюю
сессию на агента, а столкновение двух НАШИХ ходов на ней ловит существующий замок:
они-то в `ps` видны.

**Замок не разобрали.** `_logical_target()` сворачивает `:auto` → `:main`: ход на
лане автоматики по-прежнему запирает агента целиком (экран/телефон/память у него
один). Без этой свёртки развод лан незаметно отключил бы защиту от двойного подъёма.

**Чем закреплено.** `tests/test_our_turn_never_restarts_the_boss_session.py` —
5 проверок: ход по имени агента и ход по явному `:main` уезжают на `:auto`; лана
subagent не тронута; идущий ход на `:auto` виден замку как занятость `:main`
(в т.ч. цель в кавычках от шелл-обёртки); `commit_watchdog` ходит той же дверью.
Поправил устаревший assert в `test_wake_delivery_default.py`: цель теперь читается
дверью замка (`_target_of_cmdline`), а не по флагу `--agent`, которого в команде
больше нет. **Контракты: 110/110 зелёных.**

**Что осталось открытым (не мой класс).** В журнале гейтвея рядом с `activeSessions`
нет `agentId`, поэтому атрибуция столкновения по логу невозможна — подтвердить
исчезновение `reason=restart` можно только по факту отсутствия обрывов петли.
Сериализации на стороне гейтвея у нас ручки нет (в `openclaw.json` есть только
`session.reset.idleMinutes`). Восстановление после потери петли уже закрыто ранее
(1488bc5e9b37): это транспорт, лечится повтором, а не логином.
