## 4. 🔴 ГЛАВНОЕ: ТЕЛЕФОННЫЙ УЗЕЛ СЛОМАЛА ВЫДАЧА ПРАВ 13:22, А НЕ ВЕРСИЯ

Я шёл проверять `scope_mismatch` как проблему прав. Она ею и оказалась — но с обратным знаком:
**узел убит не нехваткой прав, а их выдачей.**

### Что показал стор

У устройства два токена — ролей `operator` и `node`. Сравнение с root-бэкапом
`paired.json.bak_before_admin_grant_20260823` (13:22) даёт точную дельту:

```
ДО выдачи прав (13:22)          ПОСЛЕ (сейчас)
token[node].scopes     = []     → ['operator.admin']      ← сломано ровно здесь
token[operator].scopes = [4]    → [5, +operator.admin]
device.approvedScopes  = [4]    → [5, +operator.admin]
```

У **всех остальных** узлов в сторе `token[node].scopes = []`:

```
Galaxy Tab A11+ 5G   node-token scopes = []
Pixel 10a (старый)   node-token scopes = []
Pixel 10a (живой)    node-token scopes = ['operator.admin']   ← единственный особенный, единственный сломанный
```

### Доказательство кодом, а не совпадением

`dist/device-pairing-DBBF4i61.js` при авторизации зовёт
`roleScopesAllow({role:'node', requestedScopes: entry.scopes, allowedScopes: approvedScopes})`,
а в `dist/operator-scope-compat-BVrjvlGm.js:23`:

```js
if (requested.length === 0) return true;                    // ← пустой список проходит ВСЕГДА
if (params.role.trim() !== OPERATOR_ROLE) {
    const prefix = `${params.role.trim()}.`;                // для роли node это 'node.'
    return requested.every(s => s.startsWith(prefix) && allowedSet.has(s));
}
```

Подставляем:

- **было** `scopes = []` → первая же строка возвращает `true` → узел подключался;
- **стало** `scopes = ['operator.admin']` → роль `node`, префикс `node.`,
  `'operator.admin'.startsWith('node.')` = **false** → `scope-mismatch`, **детерминированно, при каждом коннекте, навсегда**.

Там же объясняется и `scopes=0` в журнале: `resolveRoleScopedDeviceTokenScopes` для роли,
отличной от `operator`, **отфильтровывает** всё с префиксом `operator.` — от токена не остаётся
ничего. То есть выданное право не просто бесполезно узлу, оно для него **невыразимо**.

### Улики времени сходятся

```
scope_mismatch за 3 суток ДО выдачи прав : 0
scope_mismatch после                     : 1  (13:28:33, первый же коннект после рестарта)
'node not connected' за 72ч ДО           : 9   (0.13/ч)
'node not connected' за 93 мин ПОСЛЕ     : 12  (7.7/ч)  → рост в ~60 раз
```

Сообщение самого гейтвея на закрытии: `code=1008 reason=unauthorized: device token scope mismatch
(re-pair or approve scope upgrade)`.

### Почему это не заметили

Телефон **жив и достижим** (ping 100.85.178.10 — 0% потерь, 179 мс), и его роль `operator`
подключается штатно — это и есть тот самый «шумный контрол-клиент» с `question.list`.
То есть телефон в `nodes status` выглядит «paired · approved», панель отвечает, — а роль `node`
отбита. **Живая половина устройства маскировала мёртвую.**
После отказа в 13:28:33 приложение больше не пыталось: попыток `role=node` с тех пор — **0**.

### Чинится одним полем, БЕЗ рестарта гейтвея

Вернуть `tokens.node.scopes` живого Pixel (`remoteIp 100.85.178.10`) в `[]` — то есть ровно
довыдачное состояние и ровно то, что у всех прочих узлов. **Секрет токена не трогать**: телефон
хранит его у себя, и ротация (`openclaw devices rotate`) выдала бы новый токен, которого у телефона
нет, — стало бы хуже.

Рестарт гейтвея **не нужен**: `loadState()` в `device-pairing` читает `devices/paired.json`
с диска на каждый вызов, кэша нет. Достаточно правки файла и переподключения приложения
(`adb -s 100.85.178.10:5555 shell am force-stop ai.openclaw.app` + запуск; adb до телефона живой,
пакет `ai.openclaw.app` на месте).

### Почему я это НЕ применил

Правка `devices/paired.json` и остановка гейтвея **заблокированы классификатором разрешений** —
это стор учётных данных, и гейт тут прав. Обходить его я не стал. Нужна санкция Босса на одну
правку одного поля; бэкап делается той же командой.
